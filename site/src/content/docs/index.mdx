<section aria-labelledby="what">

<h2 id="what">The declarative standard for agentic workflows.</h2>

AWP describes what an agentic workflow does, within which limits it may run, under which governance it runs and what it leaves behind. Agents are not plain LLM calls; they are controlled workflows with defined capabilities, limits and responsibilities.

<div class="cols">
<div>

### Define
Agents, tools, steps, triggers and inputs in one manifest.

</div>
<div>

### Govern
Policies, approvals and budgets that a runtime enforces.

</div>
<div>

### Execute
Portable across runtimes that implement the specification.

</div>
<div>

### Audit
Standard events and decision traces for every execution.

</div>
</div>
</section>

<section aria-labelledby="compare">

<h2 id="compare">MCP connects agents to tools. A2A connects agents to agents. AWP defines how agents work.</h2>

<table>
  <caption class="sr-only">Scope of MCP, A2A and AWP</caption>
  <thead>
    <tr><th scope="col"></th><th scope="col">MCP</th><th scope="col">A2A</th><th scope="col">AWP</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">Scope</th><td>Agents ↔ tools and resources</td><td>Agent ↔ agent communication</td><td>Definition, governance, execution and audit of workflows</td></tr>
    <tr><th scope="row">Question answered</th><td>How does an agent call this tool?</td><td>How do two agents talk to each other?</td><td>What may this workflow do, who owns it and what happened?</td></tr>
    <tr><th scope="row">Example artifact</th><td>Tool and resource definitions</td><td>Agent card, task messages</td><td>Workflow, Agent and Policy manifests, audit events</td></tr>
  </tbody>
</table>

AWP does not replace MCP or A2A. A manifest references MCP servers as tool sources and A2A endpoints as remote agents.

</section>

<section aria-labelledby="manifest">

<h2 id="manifest">One file describes the workflow, its limits and its rules.</h2>

<Code code={fixer} lang="yaml" title="vulnerability-fixer.workflow.yaml" />

1. `metadata`: name, version, owner, classification and risk level.
2. `spec.budget`: cost, steps, duration, tokens, tool calls, retries, concurrency.
3. `spec.agents` and `spec.mcpServers`: who acts and with which tools.
4. `spec.workflow`: steps with `dependsOn`, including a `command` step.
5. `spec.permissions` and `spec.policies`: what is allowed, what is not.

<h2 id="sec">Trusted agent supply chain. Know what runs before you let it run.</h2>

<div class="cols">
<div>

### Secrets by reference
Manifests name secrets and reference them with `secretRef`. A literal token in a manifest is rejected.

</div>
<div>

### Integrity
Immutable versions, manifest digests, signatures, provenance, trusted registries and dependency declarations.

</div>
<div>

### Fail closed
Unknown fields in governance sections and policies that cannot be evaluated deny instead of allow.

<section aria-labelledby="conf">

<h2 id="conf">Build your own AWP runtime.</h2>

AWP is not tied to OpenAgentix. A runtime declares which conformance profiles it implements and which optional features it does not support. A public conformance test suite for manifests is in the repository.

<div class="split">
<dl>
  <dt><code>core</code></dt><dd>Parse and validate manifests, execute the step graph, enforce budgets and permissions.</dd>
  <dt><code>governance</code></dt><dd>Ownership, data policy, model policy, approvals, risk levels, environments, policies.</dd>
  <dt><code>audit</code></dt><dd>Event envelope, all event types, decision and reproducibility records.</dd>
  <dt><code>security</code></dt><dd>Digests, signatures, image pinning, isolation, secret redaction.</dd>
  <dt><code>mcp</code></dt><dd>MCP servers as tool sources, action identifiers per tool call.</dd>
  <dt><code>a2a</code></dt><dd>Remote agents with verified agent cards.</dd>
</dl>
